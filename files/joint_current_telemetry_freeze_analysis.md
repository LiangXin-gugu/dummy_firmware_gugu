# 关节电流遥测：不灵敏跟随指令 + 各关节表现差异 的成因与解决

> 本文汇总以下问题的分析结论：
> 1. 为什么 `#GET_CURRENT` 读到的关节电流**不灵敏跟随指令变化**——运动全程数值冻结、停稳后才离散突跳？
> 2. 为什么**各关节表现不一样**——J1/J2 电流几乎每拍刷新，J4/J5（尤其）长期冻结？明明都在同一条 CAN 总线上。
> 3. 这是不是"200Hz × 6 重发 MoveJoints 把总线占满"导致的？正常吗？
> 4. J4/J5 电流"不跟随指令"到底是**物理特性**（谐波减速器 stick-slip）还是**测量假象**？
> 5. 怎样才能**公平地**测到运动过程中的真实电流？

---

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 总线是否被占满 | **否**。1Mbps 下最坏负载约 **34%**（位置帧 + 位置 ACK + 电流帧），带宽余量充足 |
| 运动中电流冻结 | **真实现象，但不是物理、也不是控制滞后**，而是**遥测饥饿**（缓存陈旧） |
| 前后关节为何不一样 | **不是带宽饱和**（饱和会让所有关节一起糊），而是 **CAN ID 优先级仲裁 + 丢仲裁不重传**造成的**按节点号单调递减的刷新梯度** |
| 是不是 42/35 固件不同导致 | **否**。两套固件在 0x07/0x21/CAN 配置上行为完全一致，差异**纯粹来自节点 ID** |
| J4/J5 "电流小、不跟随" | **两个原因叠加**：①物理上本就很小（轻载腕关节 + 50:1 反射力矩极小 + 谐波摩擦吸收）；②运动中遥测被饿死（高节点 ID）。二者同向，极易误判 |
| 旧结论"J4/J5 = stick-slip 物理" | **被遥测饥饿污染，需存疑并重测**。只有 J1/J2（低 ID、缓存新鲜）的电流数据在旧测试里可信 |

## 2. 背景：关节电流数据是怎么来的

### 2.1 focCurrent 的物理含义

`#GET_CURRENT` 返回的不是实测相电流，而是 **DCE 控制器基于位置偏差 `pError` 计算出的输出值 `focCurrent`**（电机端 `GetFocCurrent()` 返回 `focCurrent/1000`，单位 mA→A）。它**间接反映关节负载力矩**：负载越大、偏差越大，控制器输出的电流指令越大。

### 2.2 关节硬件配置

| 关节 | 电机固件 | 减速器 | 力臂/负载 | 电流量级 |
|---|---|---|---|---|
| J1–J3 | `dummy-42motor-fw` | 谐波 50:1 | 长力臂、重力/摩擦主导 | 较大（近似与运动同频） |
| J4–J5 | `dummy-35motor-fw` | 谐波 50:1 | 短力臂、轻载腕关节 | **很小**（~0.007–0.09A） |
| J6 | `dummy-35motor-fw` | 直驱（reduction=1） | 最末端 | 小 |

谐波减速器**几乎无背隙**，但**静摩擦大、有扭转迟滞（Lost Motion）、通常不可反驱**。轻载关节在低速下的小力矩会被静摩擦/迟滞吸收，产生 **stick-slip（粘滑）** 抖动——这是**真实物理**，但只有在遥测不被饿死时才测得准。

### 2.3 电流查询与刷新链路

```text
上位机  #GET_CURRENT
  │  (USB ASCII)
  ▼
OnUsbAsciiCmd → 读缓存 dummy.GetMotorCurrents()          [ascii_protocol.cpp L109-119]
  │  仅读 motorJ[i]->current，无阻塞、无 CAN 增量          [dummy_robot.cpp L277-283]
  ▲
  │ 缓存由下面这条后台链路刷新：
  │
TIM7 200Hz 中断 → ThreadControlLoopFixUpdate              [main.cpp L20-85]
  ├── 每 4 拍(50Hz): dummy.UpdateAllCurrent()             [main.cpp L28,L40-41]
  │     └── motorJ[ALL]->UpdateCurrent()  广播 0x21        [dummy_robot.cpp L198-201]
  │           └── StdId = 0<<7 | 0x21 = 0x21  单帧广播      [ctrl_step.cpp L259-265]
  │                 ▼ 6 个电机滤波器 mask=0 全收，各自抢答：
  │                 motor: case 0x21 → GetFocCurrent()
  │                        回帧 StdId = (canNodeId<<7)|0x21  [interface_can.cpp 0x21]
  │                 ▼
  │           OnCanMessage: case 0x21 → memcpy 到 motorJ[id]->current  [can_protocol.cpp L31-33]
  │
  └── 点到点模式(SEQ/INTERRUPTABLE)每拍: dummy.MoveJoints(targetJoints)  [main.cpp L57-59]
        └── 6 × SetAngleWithVelocityLimit → CAN 0x07        [dummy_robot.cpp L66-73]
              ▼ motor: case 0x07 "Always Need ... ACK" → 无条件回 0x23   [interface_can.cpp L87-107]
              ▼ OnCanMessage: case 0x23 → UpdateAngleCallback  [can_protocol.cpp L35-37]
```

**关键：`GET_CURRENT` 只是读缓存。缓存新鲜与否，完全取决于那条 50Hz 的 0x21 广播回帧能否成功抵达主机。** 一旦回帧被丢，主机就反复读到运动前的旧值——表现为"冻结"。

## 3. 问题现象

### 现象 1：运动中电流精确冻结，停稳后离散突跳

阶跃测试（`current_log_20260910_132922.npz`，脚本 `test_motor_current_new.py`）中，J3 的一次阶跃（cmd16）：

- 运动全程（约 2.3s）电流**冻结在 +0.112A**，纹丝不动；
- 运动停止、稳定约 1–3s 后，电流**离散突跳到 −0.151A**。

这不是控制滞后（滞后应是连续、平滑地追赶），而是**缓存长期不更新 + 偶尔成功刷新一次**的典型特征。

### 现象 2：J4/J5 电流"几乎无变化"

同一测试中，J4/J5 单独阶跃时，电流随指令的变化**极不明显甚至看不出变化**。

### 现象 3：选择性刷新梯度（决定性证据）

扫描每个运动窗口内**各关节电流缓存的刷新次数**（变化事件数）：

| 运动窗口 | J1 | J2 | J3 | J4 | J5 | J6 |
|---|---|---|---|---|---|---|
| J3 运动 (cmd16, ~2.3s) | **53** | 6 | **0**(运动中) | 0 | 0 | 0 |
| J2 运动 (cmd8, ~3.1s) | **65** | **1**(运动中) | 0 | 0 | 0 | 0 |
| J4 运动 (cmd1) | 10 | 1 | 0 | **0**(运动中) | 0 | — |

这是一条**按节点号单调递减的刷新梯度**：J1 几乎每拍刷新，越靠后越饿，**正在运动的那个关节自己冻得最死**。

### 现象 4：主机反馈采样率下降

运动期间主机端反馈采样率从 ~50Hz 掉到 **34.8Hz**——说明下位机应答/回流确实被拖慢，但注意：**这是访问不公平的表现，不是带宽跑满**（见 4.1）。

## 4. 根因分析

### 4.1 先排除"总线饱和"

先确认波特率（两侧必须一致，否则根本通不了）：

| 节点 | 时钟 | 位时序 | 波特率 |
|---|---|---|---|
| 主机 F405 `can.c L42-46` | APB1 42MHz | Prescaler=7 ×（1+BS1_3+BS2_2）=6TQ | **1 Mbps** |
| 电机 F103 `can.c L49-53` | APB1 36MHz | Prescaler=4 ×（1+BS1_5+BS2_3）=9TQ | **1 Mbps** |

再算点到点运动（0x07 每拍重发）时的**最坏**帧率（一帧 8 字节标准帧 ≈ 111 bit + 位填充 ≈ ~122µs @1Mbps）：

| 方向 | 帧来源 | 帧率 |
|---|---|---|
| 主机 TX | 位置命令 0x07（200Hz×6） | 1200/s |
| 主机 TX | 电流广播 0x21（50Hz×1） | 50/s |
| 主机 RX | 位置 ACK 0x23（每个 0x07 无条件回一帧） | 1200/s |
| 主机 RX | 电流 ACK 0x21（50Hz×6） | 300/s |
| **合计（最坏）** | | **~2750/s** |

`2750 × 122µs ≈ 336ms/s ≈ **34%**`。**即使按最坏情况估算，总线也只用了约三分之一，远未饱和。** 而且丢仲裁的帧不会占满整帧时间，实际成功帧负载更低。

> **订正**：早期分析曾说"重发 MoveJoints 占满总线带宽"，此措辞不准确——带宽不是瓶颈。真正的瓶颈在**接收侧的访问公平性**。

### 4.2 真因：遥测访问不公平（不是带宽，是仲裁）

同一条总线，为什么 J1 新鲜、J6 冻结？因为电流查询用的是**"广播 + 抢答"**模式，而 CAN 的仲裁规则天然偏袒低 ID：

**① 广播抢答**：`UpdateAllCurrent()` 发的是 `motorJ[ALL]`（伪节点 0）的单帧广播 `StdId=0x21`。电机滤波器 mask 全 0，6 个电机**同时**收到、**同时**回帧，各用自己的 ID。

**② CAN ID 优先级**：`StdId = nodeID<<7 | cmd`，节点号越小、ID 越小、仲裁优先级越高：

| 回帧类型 | J1 | J2 | J3 | J4 | J5 | J6 |
|---|---|---|---|---|---|---|
| 电流 ACK (0x21) | 0xA1(161) | 0x121(289) | 0x1A1(417) | 0x221(545) | 0x2A1(673) | **0x321(801)** |
| 位置 ACK (0x23) | 0xA3(163) | 0x123(291) | 0x1A3(419) | 0x223(547) | 0x2A3(675) | 0x323(803) |

多帧碰撞时，**低 ID 永远先赢**。以 J6 电流帧（801）为例，比它优先级高的有 10 个（J1–J5 的电流帧 + J1–J5 的位置帧），它几乎永远排在最后。

**③ 两侧都关了自动重传（NART）**：主机 `can.c L50` 与电机 `can.c L57`（35/42 均如此）都是 `AutoRetransmission = DISABLE`。**输掉仲裁的电机不会重发**——这一拍的电流就永久丢了，主机缓存保持旧值。低 ID 的 J1 几乎每拍都赢 → 永远新鲜；高 ID 的 J6 几乎每拍都输 → 永久冻结。

**④ 位置 ACK 淹没电流 ACK**：`case 0x07` 是 **"Always Need Position & Finished ACK"**（`interface_can.cpp L98`），**无条件**回 0x23。运动中每拍 6 个位置命令 → **1200 帧/s 的 0x23 位置 ACK**，而电流 ACK 只有 300 帧/s。二者 ID 相近、争同一批 FIFO 与仲裁，**电流回帧被 4 倍于它的位置回帧挤掉**。

**⑤ 3 深 RX FIFO + 每帧重回调**：主机 bxCAN 每个 RX FIFO 仅 **3 格**，且 `ReceiveFifoLocked=DISABLE`（满了丢新帧）。而 `OnCanMessage` **每收一帧都要跑一遍 6 循环的 `UpdateJointAnglesCallback()`**（`can_protocol.cpp L47`），排空慢。6 个电机在一个突发里抢答时，J1/J2/J3 先进 FIFO，等 J4/J5/J6 到时 FIFO 已溢出被丢——**与仲裁梯度同向叠加**。

**⑥ 运动节点应答更晚**：正在运动的关节控制环忙，响应 0x21 有额外延迟 → 更晚上总线 → 更容易输仲裁 → **运动中自己的电流冻得最死**（这正是 J3 运动时冻结、停稳后才跳的原因）。

**六个因素全部指向同一方向**：低节点 ID 垄断刷新，高节点 ID 与运动中的关节被饿死。所以"前不冻、后冻"**恰恰是仲裁假象的指纹**——如果是带宽饱和，应该是**所有关节一起糊**，而不是这种干净的按 ID 梯度。

### 4.3 物理层面的正常差异（另一半原因）

即使遥测完全公平，J4/J5 电流**本来就小**：

- 腕关节**力臂短、负载轻**；
- 经 **50:1 谐波减速**后，负载反射到电机轴的力矩**极小**；
- 小力矩被谐波减速器的**静摩擦/扭转迟滞吸收**，低速下呈 **stick-slip** 随机抖动。

而 J1–J3 力臂长、重力/摩擦主导，电流大且与运动近似同频。**这部分差异是正常的物理特性，与遥测无关。**

### 4.4 为什么极易误判

"各关节表现不一样"是**两个独立原因同向叠加**的结果：

| | J1–J2 | J4–J5 |
|---|---|---|
| 物理电流量级 | 大 | **小** |
| 遥测新鲜度（节点 ID） | 高（低 ID，新鲜） | **低（高 ID，冻结）** |
| 观测到的"跟随性" | 好 | **差** |

物理小 + 遥测冻结，两者都让 J4/J5 看起来"电流不跟随指令"，因此很容易把**遥测假象**误当成**物理结论**（stick-slip）。要分离二者，必须先修遥测公平性（见第 5 节）。

## 5. 解决方案

### 5.1【已验证·固件】电流/角度/温度查询从广播改 per-joint 串行

**核心改动**（已在 `dummy_robot.cpp` L178-224 实现）：把三个查询函数从 `motorJ[ALL]`（广播到 nodeID=0）改为 for 循环逐个节点独立查询（每个电机用自己的 nodeID）。

```cpp
// ✅ 修改前：广播抢答模式
void DummyRobot::UpdateAllCurrent()
{
    motorJ[ALL]->UpdateCurrent();  // StdId = 0<<7 | 0x21 = 0x21 (广播)
}

// ✅ 修改后：per-joint 串行查询（同一 FixUpdate tick 内发完）
void DummyRobot::UpdateAllCurrent()
{
    for (int i = 1; i <= 6; i++) {
        motorJ[i]->UpdateCurrent();  // StdId = (i<<7) | 0x21 (独立查询)
    }
}
```

同样改进了 `UpdateJointAngles()` 和 `UpdateAllTemp()`，三者都在同一个 5ms 周期内通过 for 循环快速发出。

**效果验证**：所有关节电流现在能灵敏跟随末端加载变化，没有 J4/J5 冻结的梯度现象。**CAN 仲裁冲突是主因**。

#### 为什么有效？（对比两种模式的 CAN 行为）

| 模式 | 主机发送行为 | 电机响应行为 | CAN 总线上的结果 |
|---|---|---|---|
| **广播模式（修改前）** | 一次 0x21 广播 → 6 电机同时收 | 几乎同时回复各自的 0x21（StdId=0xA1..0x321） | **硬碰撞**：CAN 仲裁强制按 ID 顺序发，但所有 TX 决策在同一微秒→高 ID 必输→NART→永久丢帧 |
| **Per-joint 模式（修改后）** | 依次发 6 个独立 0x21（间隔~50μs，stdid 不同） | 每个电机等自己的查询帧才回复 | **软碰撞**：每个电机的回复被它自己的查询触发，回复时间点有微小差异（虽然只有几微秒），给 CAN 仲裁留缓冲空间→低 ID 先发、高 ID 后发，**全部都能成功送达** |

关键点：**不是时序隔离**（仍然在同一个 5ms tick 内），而是**每个电机的 0x21 回帧被它自己的 0x21 查询帧"预热"了**，回复时间错开，避免了"全部同时决定回复"的物理层硬撞车。CAN 仲裁因此能让所有回帧按 ID 顺序依次上总线，而不是高 ID 直接被淹死。

#### 对比方案评估

| 方案 | 实现难度 | 负载增量 | 公平性改善 | 推荐度 |
|---|---|---|---|---|
| **Per-joint 串行（已验证）** | 低（改 3 行代码） | +150% 查询帧率（50×1→50×6/s），仍远低于带宽上限 | 彻底消除仲裁冲突 | ⭐⭐⭐⭐⭐ |
| **AutoRetransmission=ENABLE** | 中（改 can.c + 两侧固件） | 相同 | 部分缓解（重传能补救输掉的），但增加总线和延迟 | ⭐⭐⭐ |
| **Rx FIFO 深度扩展** | 高（需硬件支持/外部缓冲） | 无 | 仅缓解溢出，不能解决仲裁冲突本身 | ⭐⭐ |

**结论**：Per-joint 串行查询**最简单有效**，且不改变 CAN 物理配置，兼容性好。

### 5.2【理论可行·固件】AutoRetransmission=ENABLE 作为备选

CAN 协议定义中的 `AutoRetransmission`（自动重传）选项如果设为 ENABLE，当某个电机电流的 0x21 回帧输掉仲裁时，它会**自动重传直到成功**。这与 NART（禁用自动重传）的致命区别是：

- **NART（当前）**：输掉仲裁 = 永久丢帧 → 缓存陈旧；
- **ART（提议）**：输掉仲裁 = 稍后重试 → 最终能刷新，只是偶尔有延迟。

**理论上可行，但有代价**：

1. **需要两侧固件一致改配置**（主机 and 电机 must both enable ART），否则通信失效；
2. **增加 CAN 总线负载**（重传帧可能叠加位置 ACK）；
3. **引入不可控延迟**（高 ID 电机可能输掉多次才成功，电流刷新更不稳定）；
4. **不影响仲裁优先级本身**，只是"迟到的新鲜"而非"及时的新鲜"。

**综合对比**：Per-joint 串行查询是**确定性方案**（每次刷新都准时可达），ART 启用是**概率性方案**（刷新可能延迟但仍最终可达）。优先推荐前者。

### 5.3【补充说明】为什么没改 Rx FIFO 也能工作？

RX FIFO 深度（bxCAN 标准每级 3 格）确实浅，但不是本问题的根因：

- **原理解释**：FIFO 溢出通常发生在**突发多帧同时到达**时（比如 6 个 0x21 回帧几乎同时进 RX 队列）。Per-joint 串行查询虽然没有显式的时间隔离，但它让回帧**分散在不同微秒到达**（因为每个查询帧触发的回复有时间差），FIFO 来得及逐个处理。
- **关键洞察**：瓶颈不在**接收侧容量**，而在**发送侧的协调**——广播模式下，所有电机在同一时刻决定回复，导致"突发流量"；而 per-joint 模式下，每个电机的回复被它自己的查询"错峰"触发，流量变平滑。
- **实验证据**：如果你测试发现电流刷新又出现梯度（极少数情况下），再考虑扩展 FIFO（可能需要 DMA+ 外部缓冲或更高性能的 MCU）。目前来看，**改发送端比扩接收端更有效**。

### 5.2【固件】目标未变时不重发 MoveJoints

点到点模式下，`targetJoints` 到位后目标不再变化，但 FixUpdate 仍每拍重发 6 帧 0x07（`main.cpp L57-59`），既产生 1200 帧/s 的位置流量，又触发 1200 帧/s 的 0x23 ACK 淹没电流回帧。可改为**仅在目标变化时下发**，或到位后停止重发：

- 直接砍掉运动段结束后那部分位置帧与其 ACK；
- 减轻 RX FIFO 压力，给电流回帧腾出时隙。

### 5.3【固件·可选】削弱位置 ACK 洪水

`case 0x07` 的无条件 0x23 ACK 在 200Hz 重发下是 1200 帧/s 的纯冗余（主机每拍都已知目标）。可选：

- 0x07 改为**条件 ACK**（仅到位时回，类似 `case 0x05` 的 `if (_data[4])`）；或
- 高速流式运动改用 **0x08 轨迹模式**（`case 0x08` **完全不回 ACK**，`interface_can.cpp L108-117`），RX 侧立刻安静，电流遥测自然恢复。
  - 注意：`dummy-35motor-fw`（J4–J6）**未实现 case 0x08**，若走此路需先给 35 固件补上轨迹命令。

### 5.4【分析侧】剔除陈旧样本

在修复固件前分析已有数据时：

- **检测刷新时刻**：某关节电流值发生变化的时刻才是"缓存真正更新"的时刻，两次变化之间都是陈旧值；
- **剔除冻结段**：把运动中长时间不变的电流样本标记为 stale 并排除，**不要**拿它去算相干比/std/相关性；
- **优先信 J1/J2**：低节点 ID 的电流在旧数据里相对可信，可作为对照基准。

### 5.5 公平重测 J4/J5 的物理特性

要确认 J4/J5 到底有没有 stick-slip（而非遥测假象），需在**修好 5.1 逐节点轮询之后**重测，或：

- 在**电机端本地**记录 focCurrent（不经过主机 CAN 遥测），彻底避开总线竞争；
- 或用**示波器/电流探针**直接测相电流做基准对照。

## 6. 对既有结论的订正

| 旧结论 | 订正 |
|---|---|
| "重发 MoveJoints **占满**总线带宽导致电流饿死" | 总线**未饱和**（最坏 ~34%）。真因是**广播抢答 + ID 优先级仲裁 + NART 不重传**造成的**发送端协调失败**。经 per-joint 串行查询验证，彻底消除冲突 → 电流恢复正常 |
| "正弦轨迹走 CONTINUOUS 模式，故电流正常" | **错**。`test_sine_trajectory.py` 的 `set_command_mode(3)` 被注释，实际走 **INTERRUPTABLE**（`move_j` → 0x07），同样每拍重发、同样有 0x23 ACK 洪水、同样饿死电流。不存在"轻载对照组" |
| "J4/J5 电流不跟随 = 谐波 stick-slip 物理" | **需重新评估**。之前认为 J4/J5 电流不跟随主要是遥测饥饿假象而非物理特性。现已通过改为 per-joint 串行查询验证：所有关节电流均灵敏跟随末端加载变化 → **之前的"不跟随"确实是测量假象**，不是 stick-slip。如要验证真正的谐波摩擦特性，需在低速小负载条件下单独测试 |
| "J1-3(42 固件) 与 J4-6(35 固件) 差异来自固件类型" | **否**。两套固件在 0x07（无条件 ACK）、0x21（电流应答）、CAN 配置（NART/1Mbps）上**完全一致**。前后关节差异**纯粹来自节点 ID 优先级**导致的发送协调问题 |

> 说明：J3 阶跃"滞后"的结论**依然成立**——它正是本机制（运动中冻结、偶尔刷新一次呈离散突跳）的表现，现在有了更完整的解释。修改后的 per-joint 串行查询方案已彻底解决此问题。

**最终结论**：关节电流"不灵敏跟随指令"和"各关节表现不一样"，主因不是总线带宽被占满（实际仅约 34%），而是电流遥测采用了**广播抢答模式**（motorJ[ALL]→nodeID=0）→ 6 电机同时回复同一广播 → CAN 仲裁强制按 ID 顺序发送但所有 TX 决策在同一微秒 → 高 ID 必输 → NART（AutoRetransmission=DISABLE）→永久丢帧。**关键洞见**：瓶颈不在接收侧（FIFO 容量）而在**发送侧的协调**——广播触发让所有电机在同一时刻决定回复，造成物理层硬撞车；而改为 per-joint 串行查询后，每个电机的回复被它自己的查询"预热"触发，回复时间有微小差异（几微秒），给 CAN 仲裁留缓冲空间，让所有回帧都能按 ID 顺序依次成功送达。

## 8. 一句话总结

关节电流"不灵敏跟随指令"和"各关节表现不一样"，**主因不是总线带宽被占满（实际仅约 34%），而是电流遥测采用了"广播抢答 + 低 ID 优先 + 丢仲裁不重传"的访问方式**：J1 几乎每拍赢仲裁保持新鲜，J4/J5/J6 与运动中的关节持续输仲裁、缓存被冻结，再叠加 0x07 位置 ACK 洪水的挤占。**"前不冻、后冻"正是 CAN ID 优先级的直接指纹，而非物理差异、更非带宽饱和。** 物理上 J4/J5 电流本就很小，与遥测饥饿同向叠加，导致此前把测量假象误读为 stick-slip 物理——需用逐节点轮询重测才能分离。
